# Mission — Refonte UX/UI de l'écran principal de Prosperity

Tu travailles sur une application web existante qui adapte le jeu de plateau **Prosperity**.

L'application est déjà fonctionnelle.

Ton objectif n'est PAS de refaire l'application depuis zéro ni de modifier les règles du jeu.

Tu dois améliorer fortement l'expérience utilisateur de l'écran principal afin que :

- un joueur découvrant Prosperity comprenne rapidement ce qui se passe ;
- un joueur expérimenté puisse jouer rapidement sans aides intrusives ;
- l'écran reste épuré malgré la quantité d'informations du jeu ;
- l'interface ressemble à un véritable jeu de plateau numérique et non à un dashboard ou une application métier ;
- la direction artistique actuelle soit conservée et améliorée.

La priorité absolue est :

1. UX ;
2. lisibilité ;
3. hiérarchie visuelle ;
4. compréhension immédiate du tour ;
5. qualité du design ;
6. fluidité des interactions.

---

# 1. Avant toute modification

Commence par analyser l'application existante.

Identifie notamment :

- les composants constituant l'écran principal ;
- la gestion de l'état du jeu ;
- le fonctionnement du tour ;
- les composants des technologies ;
- le plateau individuel ;
- le système de sélection/achat d'une technologie ;
- les actions du joueur ;
- le panneau latéral droit ;
- la barre inférieure ;
- la gestion des tooltips/modales ;
- les styles globaux et tokens de design existants.

Ne réécris pas inutilement des éléments qui fonctionnent.

Réutilise autant que possible :

- les composants existants ;
- les modèles de données ;
- le moteur de règles ;
- les icônes ;
- les illustrations ;
- les styles ;
- les animations existantes.

Évite absolument l'over-engineering.

Ne change pas la stack technique.

---

# 2. Structure générale à conserver

L'écran actuel est organisé autour de trois grandes zones.

Cette structure doit être conservée :

## Gauche — Ma nation

Contient notamment :

- les statistiques actuelles ;
- le plateau individuel ;
- les bâtiments construits ;
- la pollution ;
- les points de prospérité révélés.

## Centre — Technologies et recherche

Contient :

- la recherche Énergie ;
- la recherche Écologie ;
- les niveaux 1 à 6 ;
- les technologies disponibles ;
- les prix ;
- les marqueurs de recherche du joueur.

## Droite — Contexte du tour

Contient actuellement :

- Révélation ;
- Décompte ;
- Actions ;
- technologie révélée ;
- résultat du décompte ;
- informations contextuelles.

## Bas — Commandes

Contient :

- les actions disponibles ;
- le nombre d'actions restantes ;
- la validation / fin de tour.

Ne transforme pas cette vue en dashboard à cartes multiples.

L'écran doit continuer à évoquer un plateau de jeu.

---

# 3. Principe UX fondamental

À n'importe quel moment, le joueur doit être capable de répondre immédiatement à :

> « Qu'est-ce que je dois faire maintenant ? »

La phase actuellement active doit donc dominer visuellement.

Le reste de l'interface doit devenir légèrement secondaire sans disparaître.

Éviter que plusieurs CTA principaux concurrents soient visibles simultanément.

---

# 4. Boucle de tour à rendre extrêmement claire

Un tour suit les phases :

1. Révélation d'une technologie ;
2. Décompte du symbole révélé ;
3. Deux actions du joueur ;
4. Fin du tour.

Le stepper actuel :

- Révélation
- Décompte
- Actions

doit être conservé et amélioré.

Il doit clairement distinguer :

- phase terminée ;
- phase actuelle ;
- phase future.

Exemple visuel :

    ✓ Révélation
    ● Décompte
    ○ Actions

Ne crée pas un gros wizard prenant toute la place.

Cela doit rester compact et élégant.

---

# 5. Un seul CTA principal

Actuellement plusieurs contrôles peuvent entrer visuellement en concurrence :

- « Jouer mes deux actions »
- les quatre actions
- « Terminer le tour »

Refondre cette logique.

Il doit exister un seul CTA principal permettant de progresser dans le tour.

Exemples :

Pendant le décompte :

    Continuer vers mes actions →

Pendant les actions :

    Action 1 sur 2

puis :

    Action 2 sur 2

Après les deux actions :

    Terminer le tour ✓

Le CTA doit rester approximativement au même emplacement afin que le joueur apprenne rapidement où regarder.

Supprimer les CTA intermédiaires devenus inutiles.

---

# 6. Repenser visuellement les deux actions du joueur

Un joueur possède exactement deux actions pendant sa phase d'actions.

Il peut effectuer :

- deux actions différentes ;
- ou deux fois la même action.

Afficher très clairement leur état.

Exemple :

    ● ●   2 actions disponibles

Après la première :

    ✓ ●   1 action disponible

Après la seconde :

    ✓ ✓   Actions terminées

Éviter les représentations ambiguës.

Le joueur ne doit jamais se demander :

- combien d'actions il lui reste ;
- s'il peut répéter une action ;
- si son action a bien été comptabilisée.

---

# 7. Actions principales

Les quatre actions sont :

- Revenu : +100 €
- Dépolluer : retirer 1 pollution
- Recherche : avancer de 1
- Acheter : acheter une technologie

Pendant la phase Actions, elles doivent devenir des contrôles réellement importants.

Présenter par exemple :

    Revenu
    +100 €

    Dépolluer
    −1 pollution

    Recherche
    +1 niveau

    Acheter
    une technologie

Utiliser les icônes déjà présentes lorsque possible.

Les boutons doivent être :

- immédiatement reconnaissables ;
- suffisamment grands ;
- très lisibles ;
- utilisables au clic ;
- compatibles tactile si possible.

Pendant Révélation ou Décompte :

- soit les masquer ;
- soit fortement réduire leur importance visuelle.

Éviter d'afficher des boutons désactivés comme éléments majeurs de l'écran.

---

# 8. Ajouter le suivi des décomptes de la décennie

Ajouter une information stratégique compacte indiquant quels décomptes ont déjà eu lieu pendant la décennie actuelle.

Dans chaque décennie normale, suivre :

- Énergie ;
- Écologie ;
- Capital ;
- Recherche ;
- Prospérité.

Exemple :

    Décomptes 1970

    ⚡ ✓    🌿 ○    € ✓    🔬 ○    PP ○

ou une représentation visuelle équivalente.

Cette information doit être :

- très compacte ;
- immédiatement lisible ;
- proche de la décennie / du compteur de tours ;
- discrète pour le novice ;
- très utile pour le joueur expérimenté.

Ne pas créer un nouveau gros panneau.

Pour 2030, prendre correctement en compte le décompte supplémentaire prévu par les règles.

---

# 9. Transformer le panneau droit en inspecteur contextuel

Le panneau droit ne doit plus contenir en permanence de simples textes d'ambiance.

Il doit devenir la zone naturelle où afficher les détails du contexte actuel.

Son contenu dépend de ce que fait le joueur.

## Aucun élément sélectionné

Afficher :

- la phase actuelle ;
- éventuellement un conseil très court ;
- éventuellement le texte d'ambiance.

## Technologie venant d'être révélée

Afficher :

- illustration ;
- nom ;
- type ;
- niveau ;
- symbole de décompte ;
- effets importants.

## Décompte

Afficher clairement :

- type du décompte ;
- calcul ;
- résultat.

Exemple :

    Décompte Capital

    1 symbole Capital
    × 100 €

    +100 €

Le résultat doit être évident.

## Technologie sélectionnée

Le panneau devient un inspecteur détaillé de cette technologie.

## Bâtiment du territoire sélectionné

Afficher ses informations détaillées.

Éviter d'ouvrir une modale pour les informations courantes.

Le panneau droit doit remplacer la majorité des modales.

---

# 10. Inspection détaillée d'une technologie

Lorsqu'une technologie est sélectionnée dans le marché, afficher dans le panneau droit :

- nom ;
- illustration agrandie ;
- catégorie ;
- niveau de recherche ;
- prix actuel pour le joueur ;
- explication du prix ;
- effets ;
- emplacement(s) possible(s) ;
- conséquences estimées sur les statistiques du joueur.

Exemple :

    Train à grande vitesse

    Transport
    Écologie — Niveau 3

    Prix actuel : 300 €

    Votre recherche :
    niveau 1

    100 € de base
    + 2 niveaux × 100 €
    = 300 €

    Effets
    [icônes réelles de la technologie]

    Après construction

    Énergie
    +1 → 0

    Écologie
    -1 → +1

    Emplacements disponibles
    C1 · D1

    [ Acheter — 300 € ]

Les chiffres doivent évidemment être calculés à partir du véritable état du jeu.

Ne hardcoder aucun exemple de valeur.

---

# 11. Prévisualisation avant achat

C'est une fonctionnalité UX prioritaire.

Lorsqu'une technologie est sélectionnée :

calculer et afficher ce que deviendrait le territoire si elle était construite.

Cela inclut notamment :

- énergie avant → après ;
- écologie avant → après ;
- autres effets immédiatement quantifiables ;
- technologie éventuellement recouverte ;
- effets de la technologie recouverte qui seront supprimés.

Ne modifie évidemment pas réellement l'état du jeu avant confirmation.

Cette fonctionnalité doit simplement permettre au joueur de comprendre son choix.

---

# 12. Placement d'une technologie

Lorsqu'une technologie doit être placée sur le territoire :

mettre en évidence uniquement les emplacements valides.

Les emplacements valides doivent être clairement cliquables.

Les emplacements impossibles doivent rester visibles mais devenir secondaires.

Afficher éventuellement :

    Choisissez où construire cette technologie

Si placer la technologie remplace un bâtiment existant :

indiquer clairement ce qui sera remplacé.

Avant validation, afficher les changements de statistiques.

Éviter toute modale inutile.

---

# 13. Technologies achetables

Améliorer la lecture du marché.

Distinguer visuellement plusieurs états sans créer une explosion de couleurs.

Par exemple :

### Achetable immédiatement

Le joueur possède assez d'argent.

### Potentiellement atteignable pendant ce tour

Exemple :
le joueur possède 200 €, une technologie coûte 300 €, mais une action Revenu permettrait d'atteindre 300 € avant la seconde action.

Cette technologie ne doit pas être simplement présentée comme impossible.

### Impossible pendant ce tour

Le joueur ne peut pas réunir les conditions nécessaires avec ses actions restantes.

Ces états doivent rester subtils.

Ne transforme pas l'application en assistant stratégique qui choisit à la place du joueur.

L'interface doit montrer les possibilités, pas recommander la meilleure stratégie.

---

# 14. Plateau individuel

Ne pas agrandir massivement toutes les tuiles.

Le plateau doit rester suffisamment compact pour conserver l'ensemble de la partie à l'écran.

En revanche, chaque bâtiment doit pouvoir être sélectionné.

Lorsqu'un bâtiment est sélectionné :

afficher dans le panneau droit :

- nom ;
- type ;
- effets ;
- statistiques apportées ;
- règles particulières pertinentes ;
- s'il peut être remplacé.

Le clic doit fonctionner même si un tooltip au survol existe déjà.

Ne jamais faire dépendre une information importante uniquement du hover.

---

# 15. Pollution

Conserver la représentation actuelle sous forme de piste/disques.

Améliorer la relation entre pollution et prospérité.

Afficher par exemple :

    Pollution : 8
    1 PP découvert

ou :

    8 pollution · 1 PP découvert

Les deux informations doivent visuellement appartenir au même système.

Lorsque la pollution approche d'un niveau critique, afficher contextuellement une alerte.

Exemple :

    ⚠ Une pollution supplémentaire empêchera
    votre prochain décompte de Prospérité.

Ne pas afficher cette alerte lorsqu'elle n'est pas pertinente.

Éviter les messages anxiogènes ou permanents.

---

# 16. Progressive disclosure

Ne cherche PAS à expliquer toutes les règles en permanence.

Afficher les informations uniquement lorsqu'elles deviennent nécessaires.

Exemple :

Lors du premier achat d'une technologie plus avancée que le niveau de recherche actuel :

    Pourquoi 300 € ?

    Prix de base              100 €
    Écart de recherche 2    +200 €

    Total                     300 €

    [Compris]

Ne répète pas continuellement les mêmes explications si le joueur les a déjà comprises.

Si l'application possède déjà un système de préférences locales, l'utiliser.

Sinon, garder l'implémentation simple.

---

# 17. Onboarding novice

Ajouter un onboarding très léger pour la première partie.

Pas de tutoriel de plusieurs écrans.

Pas de vidéo.

Pas de mur de texte.

Présenter progressivement trois explications maximum pendant le premier tour.

### Étape 1

Lors de la révélation :

    Une technologie est révélée au début du tour.

### Étape 2

Lors du décompte :

    Son symbole déclenche un décompte pour tous les joueurs.

### Étape 3

Lors des actions :

    Vous disposez de deux actions.
    Vous pouvez effectuer deux fois la même.

Puis laisser le joueur jouer.

Les explications supplémentaires doivent apparaître contextuellement au moment du premier usage.

Prévoir la possibilité :

    Ne plus afficher les aides

Ne jamais bloquer inutilement le joueur expérimenté.

---

# 18. Hiérarchie visuelle

Améliorer fortement les niveaux de priorité.

Il doit exister trois niveaux.

## Niveau 1 — Action immédiate

Exemples :

- CTA principal ;
- action actuellement demandée ;
- sélection actuelle ;
- emplacement de construction.

Très visible.

## Niveau 2 — Informations nécessaires à la décision

Exemples :

- argent ;
- recherche ;
- prix ;
- énergie ;
- écologie ;
- pollution ;
- effets de technologie.

Visible mais secondaire.

## Niveau 3 — Informations de contexte

Exemples :

- texte d'ambiance ;
- explications secondaires ;
- historique ;
- libellés décoratifs.

Très discret.

Aujourd'hui trop d'éléments utilisent approximativement le même niveau de contraste.

Corriger cela.

---

# 19. Direction artistique

Conserver l'identité actuelle.

Elle doit continuer à évoquer :

- un jeu de plateau premium ;
- une publication institutionnelle ;
- le design éditorial des années 60/70 ;
- une nation en développement ;
- une esthétique écologique / industrielle élégante.

Conserver notamment :

- fond crème ;
- vert profond ;
- accents bleus et verts ;
- illustrations isométriques ;
- serif élégante pour les grands titres ;
- sans-serif lisible pour les informations fonctionnelles ;
- lignes fines ;
- ombres très légères ;
- nombreuses respirations.

Ne pas transformer l'UI en :

- dashboard SaaS ;
- UI mobile générique ;
- Material Design ;
- gros cards avec border-radius omniprésent ;
- interface néon ;
- jeu mobile cartoon ;
- design rempli de gradients.

Le résultat doit rester original et sobre.

---

# 20. Contraste et accessibilité

L'esthétique actuelle est volontairement douce mais certains éléments sont trop pâles.

Renforcer le contraste des éléments interactifs.

Faire clairement la différence entre :

- texte décoratif ;
- texte informatif ;
- contrôle interactif ;
- contrôle sélectionné ;
- contrôle indisponible.

Prévoir :

- focus clavier visible ;
- contraste suffisant ;
- zones cliquables confortables ;
- pas d'information uniquement transmise par la couleur ;
- pas d'information essentielle uniquement disponible au hover.

Les pictogrammes doivent être accompagnés d'un label ou d'un tooltip clair lorsqu'ils ne sont pas immédiatement évidents.

---

# 21. Animations

Utiliser des animations courtes uniquement pour renforcer la compréhension.

Exemples appropriés :

- technologie révélée qui rejoint le marché ;
- argent gagné ;
- pollution ajoutée ou retirée ;
- progression de recherche ;
- consommation d'une action ;
- changement d'une statistique ;
- sélection d'un emplacement.

Animations :

- rapides ;
- discrètes ;
- non bloquantes ;
- sans effets spectaculaires inutiles.

Éviter les animations purement décoratives.

---

# 22. Feedback des actions

Toute action doit produire un feedback immédiat.

Exemples :

Revenu :

    +100 €

Dépollution :

    Pollution 8 → 7

Recherche :

    Écologie 2 → 3

Achat :

    -200 €
    Énergie +1 → +3
    Écologie 0 → -1

Afficher ces informations temporairement de façon élégante.

Éviter les notifications toast pour chaque événement si le changement peut être montré directement à l'endroit concerné.

---

# 23. Écran 1920×1080

La vue principale doit rester entièrement exploitable sur un écran desktop 1920×1080.

L'objectif est de conserver simultanément :

- territoire ;
- marché ;
- recherche ;
- phase du tour ;
- actions.

Éviter le scroll vertical principal dans cette résolution.

La lisibilité doit cependant être meilleure que dans la version actuelle.

Prévoir également un comportement correct pour des résolutions desktop plus petites.

Ne cherche pas pour cette tâche à créer une version smartphone complète si elle n'existe pas déjà.

---

# 24. Ce qu'il ne faut PAS ajouter

Ne pas ajouter :

- arbre de statistiques ;
- conseiller IA ;
- recommandations de meilleur coup ;
- score de qualité d'une technologie ;
- écran de comparaison complexe ;
- journal d'événements permanent prenant beaucoup de place ;
- mini-map ;
- système de quêtes ;
- achievements ;
- animations lourdes ;
- tutoriel long ;
- modales pour chaque interaction ;
- panneaux supplémentaires permanents ;
- graphiques inutiles.

Le jeu possède déjà suffisamment de profondeur.

La mission est de mieux exposer ses règles, pas de créer de nouvelles fonctionnalités de gameplay.

---

# 25. Gestion des règles

Toutes les données affichées doivent provenir du véritable état du jeu.

Ne duplique pas les règles métier dans les composants UI si elles existent déjà ailleurs.

Créer si nécessaire des fonctions dérivées / selectors pour calculer :

- prix actuel d'une technologie ;
- possibilités d'achat ;
- technologies atteignables pendant le tour ;
- changements avant/après ;
- emplacements valides ;
- actions restantes ;
- décomptes déjà résolus pendant la décennie.

Les composants visuels ne doivent pas devenir responsables du moteur de règles.

---

# 26. Priorités d'implémentation

Implémenter dans cet ordre.

## Priorité P0

Indispensable :

1. hiérarchie du tour ;
2. stepper Révélation → Décompte → Actions ;
3. un seul CTA principal ;
4. représentation claire des 2 actions ;
5. amélioration des 4 actions du bas ;
6. panneau droit contextuel ;
7. sélection d'une technologie ;
8. prix détaillé ;
9. preview avant/après ;
10. placement avec emplacements valides ;
11. inspection des bâtiments.

## Priorité P1

Très importante :

12. suivi des décomptes de la décennie ;
13. états achetable / atteignable / impossible ;
14. feedback visuel des actions ;
15. amélioration pollution/prospérité ;
16. onboarding léger.

## Priorité P2

Polish :

17. animations ;
18. transitions ;
19. amélioration fine du responsive ;
20. accessibilité finale.

Ne commence pas par les animations.

---

# 27. Critères de validation UX

À la fin de l'implémentation, les situations suivantes doivent être évidentes sans consulter les règles.

## Cas 1

Une technologie vient d'être révélée.

Le joueur doit comprendre immédiatement :

- quelle technologie a été révélée ;
- quel symbole est décompté ;
- ce que ce décompte vient de produire ;
- qu'il va ensuite effectuer ses actions.

## Cas 2

Le joueur entre dans la phase Actions.

Il doit voir immédiatement :

- qu'il dispose de 2 actions ;
- quelles sont ses 4 possibilités ;
- qu'il peut répéter une action.

## Cas 3

Après une action.

Il doit comprendre immédiatement :

- quelle action a été effectuée ;
- son résultat ;
- qu'il reste une action.

## Cas 4

Il sélectionne une technologie.

Il doit comprendre sans calcul manuel :

- son prix ;
- pourquoi elle coûte ce prix ;
- ses effets ;
- ce qui changera s'il la construit ;
- où elle peut être construite.

## Cas 5

Il sélectionne un bâtiment existant.

Il doit comprendre :

- ce que ce bâtiment apporte ;
- son type ;
- s'il peut être remplacé.

## Cas 6

Il examine la décennie.

Un joueur expérimenté doit pouvoir identifier rapidement les décomptes déjà passés et ceux encore possibles.

---

# 28. Qualité de code

Conserver un code simple.

Préférer :

- composants UI ciblés ;
- propriétés dérivées ;
- état existant ;
- fonctions pures pour les previews ;
- CSS existant ou système de styles actuel.

Éviter :

- nouvelles dépendances sans nécessité réelle ;
- état global supplémentaire sans nécessité ;
- architecture générique prématurée ;
- moteur de workflow générique ;
- abstractions prévues pour d'hypothétiques futures fonctionnalités.

---

# 29. Méthode de travail

Travaille directement sur le projet.

Procède ainsi :

1. analyse l'existant ;
2. identifie les fichiers concernés ;
3. identifie les règles déjà implémentées ;
4. établis brièvement les modifications nécessaires ;
5. implémente ;
6. vérifie les états du tour ;
7. vérifie les interactions ;
8. vérifie les cas limites ;
9. vérifie visuellement l'écran ;
10. corrige les incohérences UX rencontrées.

Ne t'arrête pas après avoir seulement proposé du code.

Implémente réellement les changements.

Ne demande pas confirmation pour chaque modification mineure.

Si une fonctionnalité demandée existe déjà partiellement, améliore-la au lieu de créer un doublon.

---

# 30. Résultat attendu

Le résultat final doit donner cette impression :

> « Je comprends en quelques secondes où j'en suis, ce que je peux faire et ce que mon choix va provoquer. »

Pour un novice :

> le jeu doit progressivement expliquer son fonctionnement sans afficher le livret de règles.

Pour un joueur expérimenté :

> l'interface doit devenir transparente et lui permettre de réfléchir uniquement à sa stratégie.

La quantité d'informations affichée ne doit pas nécessairement diminuer fortement.

En revanche, leur **importance visuelle doit dépendre du contexte**.

C'est la priorité principale de cette refonte.
