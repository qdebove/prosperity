# Prompt agent — Passage de Prosperity Web au multijoueur réseau

Tu travailles sur une application web existante qui adapte le jeu de plateau **Prosperity**.

L'application solo est déjà fonctionnelle et son gameplay, son UX et son architecture actuelle doivent être considérés comme la base de travail.

Tu dois implémenter le **multijoueur réseau**, en conservant autant que possible le fonctionnement existant et en évitant de lier l'application à un fournisseur précis de base de données, de realtime, d'authentification ou d'hébergement.

L'objectif n'est PAS de reconstruire le jeu.

L'objectif est de transformer le jeu solo existant en jeu multijoueur propre, robuste, reconnectable et facilement déployable plus tard sur différentes infrastructures.

# 2. PRINCIPE ABSOLU : CONSERVER LE SYSTÈME ACTUEL DE PRÉPARATION DES 2 ACTIONS

C'est le point le plus important de cette évolution.

Le fonctionnement actuel permet au joueur de :

```text
préparer action 1
↓
voir son résultat potentiel

préparer action 2
↓
voir le résultat cumulé des deux actions

éventuellement :
↓
annuler action 2

ou :
↓
annuler toute la préparation

puis :
↓
VALIDER / COMMIT
```

CE COMPORTEMENT DOIT ÊTRE CONSERVÉ.

Ne transforme surtout pas le jeu en :

```text
action 1
→ immédiatement envoyée au serveur
→ immédiatement visible des autres joueurs

action 2
→ immédiatement envoyée au serveur
→ immédiatement visible des autres joueurs
```

Ce serait une régression fonctionnelle.

---

# 3. DRAFT LOCAL VS ÉTAT AUTORITAIRE

Faire une distinction explicite entre :

```text
AuthoritativeGameState
```

et :

```text
PreparedTurn / LocalDraft
```

## AuthoritativeGameState

C'est l'état officiel de la partie.

Il est contrôlé par l'autorité serveur.

Tous les joueurs doivent finir par avoir exactement le même état autoritaire.

## PreparedTurn

Il représente les actions que le joueur actif est en train de préparer.

Exemple conceptuel :

```ts
interface PreparedTurn {
    gameId: string;
    playerId: string;

    turnId: string;

    baseRevision: number;

    actions: PreparedAction[];
}
```

Cette préparation n'est PAS encore la partie officielle.

---

# 4. LES ACTIONS PRÉPARÉES RESTENT PRIVÉES

Pendant que le joueur actif prépare ses deux actions :

* les autres joueurs ne reçoivent pas ses actions ;
* les autres joueurs ne voient pas ses essais ;
* les autres joueurs ne voient pas ses annulations ;
* les autres joueurs ne voient pas quelles technologies il survole ;
* les autres joueurs ne voient pas son aperçu avant/après.

Ils peuvent simplement savoir, si utile :

```text
Quentin joue...
```

ou :

```text
En attente du joueur actif
```

Mais ne pas divulguer le contenu du draft.

---

# 5. LE MOTEUR EXISTANT DOIT RESTER UTILISÉ POUR LES APERÇUS

Le projet possède déjà une logique permettant de rejouer les actions préparées afin de calculer leur résultat potentiel.

CONSERVER CE MÉCANISME.

Conceptuellement :

```ts
const previewState = replayPreparedActions(
    authoritativeState,
    preparedActions
);
```

Le frontend peut ainsi afficher immédiatement :

* argent futur ;
* recherche future ;
* pollution future ;
* technologie future ;
* effets remplacés ;
* score éventuel ;
* résultat cumulé des deux actions.

Ne duplique aucune règle métier dans React.

L'aperçu doit continuer à utiliser le même moteur que la validation finale.

---

# 6. COMMIT ATOMIQUE DES DEUX ACTIONS

Lorsque le joueur clique sur :

```text
Terminer le tour
```

ou le bouton de validation existant :

le client envoie une seule commande logique contenant toute la préparation.

Exemple :

```ts
interface CommitPreparedTurnCommand {
    commandId: string;

    gameId: string;
    playerId: string;

    turnId: string;

    baseRevision: number;

    actions: PreparedAction[];
}
```

Dans une partie normale de Prosperity, cette commande contient les deux actions préparées.

---

# 7. LE SERVEUR DOIT REJOUER LES ACTIONS

Ne jamais faire confiance au résultat calculé par le navigateur.

Le client doit envoyer :

```text
les intentions
```

et PAS :

```text
le nouvel argent
la nouvelle pollution
le nouveau score
le nouveau plateau
```

Exemple valide :

```json
{
    "actions": [
        {
            "type": "RESEARCH",
            "track": "ENERGY"
        },
        {
            "type": "BUY_TECHNOLOGY",
            "technologyId": "...",
            "slotId": "..."
        }
    ]
}
```

Exemple INTERDIT :

```json
{
    "money": 350,
    "energyResearch": 4,
    "pollution": 6
}
```

---

# 8. VALIDATION ATOMIQUE

À réception du commit :

```text
état autoritaire actuel
        +
action 1
        +
action 2
```

doivent être rejoués par le serveur avec les règles officielles.

Si les deux actions sont valides :

```text
COMMIT ACCEPTÉ
```

et l'état autoritaire est remplacé par le résultat.

Si une action est invalide :

```text
COMMIT REFUSÉ
```

AUCUNE des deux actions ne doit être appliquée.

Il est interdit d'obtenir :

```text
action 1 appliquée
action 2 refusée
```

Le commit du tour doit être transactionnel du point de vue métier.

---

# 9. EXEMPLE

Alice possède :

```text
200 €
Recherche énergie : 2
Recherche écologie : 3
```

Elle prépare :

```text
Action 1
Recherche énergie

Action 2
Acheter technologie X
```

Son navigateur affiche localement :

```text
Recherche énergie : 3
Prix technologie : 100 €
Argent futur : 100 €
```

Bob et Charlie ne voient rien de cela.

Alice peut encore :

```text
annuler Action 2
```

ou :

```text
annuler toute la préparation
```

Lorsqu'Alice valide :

```text
COMMIT
```

le serveur reçoit :

```text
[
  Research(Energy),
  BuyTechnology(X, slotY)
]
```

Le serveur rejoue ces deux actions.

S'il obtient le même résultat légal :

```text
revision 42
→
revision 43
```

Le nouvel état devient officiel.

Bob et Charlie reçoivent alors le résultat.

---

# 10. DIFFUSION AUX AUTRES JOUEURS APRÈS COMMIT

Une fois le commit accepté :

envoyer immédiatement le nouvel état ou les événements correspondants aux joueurs connectés.

Conceptuellement :

```text
TURN_COMMITTED

playerId: Alice

actions:
  1. Research Energy
  2. Buy Technology X

revision:
  43
```

Les autres clients peuvent ensuite jouer visuellement :

```text
animation action 1
↓
animation action 2
```

même si le serveur a validé les deux actions atomiquement.

Ainsi :

```text
validation métier = atomique

présentation UX = séquentielle
```

Ces deux notions ne doivent pas être confondues.

---

# 11. LE CLIENT DU JOUEUR ACTIF REÇOIT AUSSI LA VALIDATION SERVEUR

Même si Alice a déjà vu le résultat dans son aperçu local :

le résultat officiel vient du serveur.

Après validation :

```text
draft local
↓
serveur
↓
état officiel
↓
synchronisation UI
```

Normalement les deux résultats seront identiques.

Si ce n'est pas le cas, l'état serveur gagne toujours.

---

# 12. UNDO UNIQUEMENT AVANT COMMIT

Conserver l'UX actuelle :

```text
action 1
action 2
annuler dernière action
annuler préparation
```

Tant que le joueur n'a pas validé.

Après :

```text
COMMIT ACCEPTÉ
```

le tour est définitif.

Ne pas ajouter un undo multijoueur après validation.

Cela introduirait des problèmes considérables de synchronisation et de règles.

---

# 13. SAUVEGARDE DU DRAFT LOCAL

Le fonctionnement actuel permet déjà à une préparation de survivre à un rechargement.

Conserver autant que possible cette propriété.

Le `PreparedTurn` peut rester stocké localement.

Il doit inclure au minimum :

```text
gameId
playerId
turnId
baseRevision
actions
```

Après rechargement :

si :

```text
turnId identique
ET
revision compatible
ET
joueur toujours actif
```

la préparation peut être restaurée.

Sinon :

la préparation locale doit être abandonnée et l'état serveur doit être utilisé.

Ne jamais réappliquer automatiquement un ancien draft sur un nouvel état serveur.

# 17. NE PAS SUR-ABSTRAIRE

L'objectif n'est pas de créer une architecture hexagonale académique gigantesque.

Créer des abstractions uniquement aux endroits où un fournisseur devra réellement pouvoir être remplacé.

Les frontières intéressantes sont principalement :

```text

éventuellement lobby storage
```

Pas besoin de créer une interface pour chaque classe du projet.

# 18. PERSISTENCE ABSTRAITE

Créer une abstraction correspondant aux besoins réels du serveur.

Par exemple :

```ts
interface MatchStore {
    create(match: StoredMatch): Promise<void>;

    get(matchId: string): Promise<StoredMatch | null>;

    save(
        match: StoredMatch,
        expectedRevision: number
    ): Promise<void>;

    delete(matchId: string): Promise<void>;
}
```

Ajouter éventuellement :

```ts
interface LobbyStore
```

si le lobby n'est pas naturellement stocké avec la partie.

# 19. IMPLÉMENTATION DE DÉVELOPPEMENT

Pour le moment, aucune base cloud n'est imposée.

Fournir une implémentation simple permettant le développement :


# 20. REALTIME ABSTRAIT

Le code applicatif ne doit pas dépendre directement d'un SaaS realtime.

```ts
interface RealtimeGateway {

```

Si boardgame.io possède déjà l'abstraction nécessaire, réutilise-la plutôt que d'ajouter une couche artificielle supplémentaire.

L'objectif est :

```text
changer de technologie de transport
```

sans modifier les règles du jeu.

Éviter de reconstruire boardgame.io par-dessus boardgame.io.

```ts
interface GameState {
```

```text

symbole de décompte actuel
```

## PlayerGameState

Peut contenir notamment :

```text

argent
pollution
prospérité

technologies construites
```

Adapter aux modèles existants.

Ne duplique pas les données inutilement.

```text
joueur actif
```

```text
currentPlayer = moi
```

```text
↓
```

# 25. RÉVÉLATION DE TECHNOLOGIE

La tuile révélée est déterminée par l'autorité de jeu.

Un seul client ne doit jamais décider quelle est la prochaine tuile.

Le deck complet ne doit pas être exposé inutilement aux clients.

Les clients ne doivent connaître que ce que les règles permettent de connaître.

---

# 26. RNG DÉTERMINISTE

Le projet possède déjà un mélange reproductible avec une seed.

Conserver cette fonctionnalité.

Une même :

```text
seed
+
catalogue
```

doit continuer à produire le même mélange.

L'aléatoire est généré par le moteur autoritaire.

Pas par chaque navigateur indépendamment.

---

# 27. DÉCOMPTE GLOBAL

Lorsqu'une technologie déclenche un symbole de décompte :

TOUS les joueurs concernés doivent être résolus.

Exemples :

```text
Energy
Ecology
Capital
Research
Prosperity
```

Chaque nation utilise son propre état.

---

# 28. DÉCISIONS PENDANT UN DÉCOMPTE

Certains décomptes nécessitent une décision du joueur.

Exemples déjà gérés par l'application :

```text
choisir comment régler un déficit énergétique

répartir des points de recherche
```

Créer une notion explicite de résolution en attente si nécessaire.

Exemple :

```ts
interface PendingDecision {
    id: string;
    playerId: string;
    type: PendingDecisionType;
    context: unknown;
}
```

Réutiliser les structures existantes lorsqu'elles conviennent.

---

# 29. ORDRE DE RÉSOLUTION DES DÉCOMPTES

Respecter l'ordre officiel de résolution du jeu.

Ne pas modifier la règle simplement pour rendre le réseau plus facile.

Si le moteur actuel doit être adapté pour traiter plusieurs joueurs :

le faire au niveau du moteur, avec des tests.

---

# 30. NE PAS CONFONDRE DÉCOMPTE ET ACTIONS DU TOUR

Les choix imposés par un décompte sont des résolutions du jeu.

Ils ne consomment PAS les deux actions préparées du joueur actif.

Les deux actions arrivent ensuite.

Conserver clairement cette distinction dans le modèle.

---

# 31. LES DEUX ACTIONS DU JOUEUR ACTIF SONT UN BATCH

Pendant la phase d'action :

```text
actionsRemaining = 2
```

Le joueur prépare exactement les actions autorisées par le jeu.

Exemple :

```text
Revenu + Recherche

Recherche + Recherche

Achat + Revenu

Achat + Achat
```

si les règles et l'état le permettent.

La seconde action doit être évaluée à partir du résultat virtuel de la première.

C'est essentiel.

---

# 32. EXEMPLE DE DÉPENDANCE ENTRE ACTION 1 ET ACTION 2

Un joueur peut faire :

```text
Action 1 :
Recherche écologie +1

Action 2 :
Acheter une technologie
```

Le prix ou l'accessibilité de l'action 2 peut dépendre du nouvel état produit par l'action 1.

Le preview doit donc calculer :

```text
state0
↓ action1
state1
↓ action2
state2
```

et non :

```text
action1 depuis state0
action2 depuis state0
```

Le serveur doit effectuer exactement le même calcul lors du commit.

---

# 33. TOKEN DE TOUR

Pour éviter qu'un ancien draft soit envoyé après un changement de tour, associer le draft à une identité de tour.

Exemple :

```ts
turnId
```

ou une information équivalente fournie par boardgame.io.

Le serveur doit refuser :

```text
draft créé au tour 17
envoyé pendant le tour 18
```

---

# 34. RÉVISION AUTORITAIRE

Ajouter une notion de version d'état si boardgame.io n'en fournit pas déjà une suffisamment fiable pour ce besoin.

Exemple :

```ts
revision: number
```

Le draft mémorise :

```text
baseRevision
```

Au commit :

```text
baseRevision client
```

doit correspondre à l'état à partir duquel les actions ont été préparées.

Si l'état a changé d'une manière affectant le tour :

refuser le commit.

---

# 35. NE PAS FAIRE DE REBASE SILENCIEUX

Si un joueur prépare :

```text
A
B
```

sur l'état 42

mais que le serveur est maintenant à l'état 43 :

ne rejoue PAS silencieusement ses décisions sur le nouvel état.

Retourner une erreur structurée du type :

```text
STALE_DRAFT
```

et renvoyer l'état officiel.

Une décision de joueur ne doit jamais être modifiée implicitement.

---

# 36. COMMAND ID ET DOUBLE CLIC

Chaque commit possède un identifiant unique :

```ts
commandId
```

Si :

```text
double clic
timeout réseau
reconnexion
retry
```

provoquent deux envois identiques :

le tour ne doit être validé qu'une seule fois.

Le deuxième envoi doit être reconnu comme duplicate/idempotent.

---

# 37. CLIENT NON FIABLE

Considérer le navigateur comme non fiable.

Le serveur doit vérifier notamment :

* identité du joueur ;
* joueur actif ;
* tour ;
* phase ;
* nombre d'actions ;
* légalité de chaque action ;
* argent ;
* prix ;
* niveau de recherche ;
* emplacement de technologie ;
* restrictions de transport ;
* technologie disponible ;
* décisions obligatoires non résolues ;
* état de pollution ;
* revision ;
* turnId.

Aucune règle importante ne repose uniquement sur un bouton désactivé côté UI.

---

# 38. ÉVÉNEMENTS DE COMMIT

Lors d'un commit réussi, produire suffisamment d'informations pour que les autres clients puissent représenter ce qui vient de se produire.

Exemple conceptuel :

```ts
interface TurnCommittedEvent {
    playerId: string;

    actions: PublicCommittedAction[];

    fromRevision: number;
    toRevision: number;
}
```

Les événements doivent contenir seulement des informations publiques.

---

# 39. ANIMATIONS DISTANTES

Lorsqu'un joueur distant commit :

les autres clients doivent pouvoir observer les conséquences dans un ordre compréhensible.

Par exemple :

```text
Quentin joue Recherche

[pion se déplace]

puis

Quentin achète Centrale solaire

[tuile placée]
```

Ne pas simplement téléporter silencieusement toutes les valeurs vers le nouvel état si les événements permettent une représentation claire.

Mais :

les animations restent de la présentation.

Elles ne contrôlent jamais l'état métier.

---

# 40. L'ÉTAT SERVEUR EST DÉJÀ VALIDÉ PENDANT LES ANIMATIONS

Il est acceptable que :

```text
serveur = état final
```

pendant que l'interface affiche encore :

```text
animation action 1
puis action 2
```

L'état métier et l'animation sont deux couches distinctes.

Ne bloque pas la cohérence serveur sur la durée d'une animation.

---

# 41. AUTRES JOUEURS EN ATTENTE

Pendant le tour d'un autre joueur, afficher clairement :

```text
Tour de Camille
```

et éventuellement :

```text
Camille prépare ses actions…
```

Les joueurs doivent pouvoir continuer à :

* inspecter leur territoire ;
* inspecter le plateau commun ;
* consulter les technologies ;
* consulter les règles si le jeu le permet.

Mais ils ne doivent pas pouvoir effectuer les actions réservées au joueur actif.

# 46. RECONNEXION OBLIGATOIRE

Cas à supporter :


# 47. PRESENCE ≠ GAME STATE



```ts
interface PlayerPresence {
    playerId: string;
    connected: boolean;
    lastSeenAt?: number;
}
```

La présence est une donnée réseau.

Elle n'est pas une règle de Prosperity.

# PRIORITÉ ABSOLUE

Le principe central de cette implémentation est :

> Le joueur actif manipule et prévisualise librement ses deux actions localement. Tant qu'il n'a pas validé, rien n'est officiel et les autres joueurs ne voient rien. Lorsqu'il valide, les deux actions finales sont envoyées ensemble à l'autorité serveur, rejouées avec le moteur officiel, validées atomiquement, puis seulement à ce moment-là diffusées aux autres joueurs.

Toute architecture qui ne respecte pas ce principe doit être considérée comme incorrecte.
