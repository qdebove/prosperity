# Prompt agent — Transformation de Prosperity en véritable expérience de jeu de plateau numérique

Tu travailles sur une application web existante qui adapte le jeu de plateau **Prosperity**.

L'application est déjà fonctionnelle :
- le moteur de jeu existe ;
- les règles principales sont implémentées ;
- le territoire du joueur existe ;
- les technologies peuvent être consultées et achetées ;
- les pistes de recherche, pollution, argent, score, année et tour sont présentes ;
- le déroulement des tours fonctionne ;
- une interface de règles et un éditeur de tuiles existent également, mais **ils ne font PAS partie de cette étape**.

L'application actuelle est propre visuellement mais donne encore trop l'impression d'utiliser un **dashboard / une application métier**.

L'objectif de cette étape est de transformer l'écran de partie en une **véritable expérience de jeu de plateau numérique**.

Il ne faut PAS modifier les règles de Prosperity ni réinventer le gameplay.

---

# 1. Objectif principal

Quand le joueur ouvre une partie, il ne doit plus avoir l'impression de naviguer dans une page web composée de :

- panneaux ;
- formulaires ;
- listes ;
- filtres ;
- onglets ;
- modales ;
- boutons d'application métier.

Il doit avoir l'impression d'avoir devant lui une **table de jeu interactive**.

Le joueur doit principalement :

- regarder le plateau ;
- manipuler des tuiles ;
- voir des marqueurs se déplacer ;
- voir sa pollution évoluer ;
- comprendre immédiatement l'état de la partie ;
- comprendre quelle étape du tour est en cours ;
- effectuer ses deux actions naturellement.

Le principe directeur est :

> Faire oublier l'interface et donner l'impression de manipuler Prosperity.

---

# 2. Contraintes absolues

## Conserver l'existant

Ne pas réécrire le moteur de jeu si ce n'est pas nécessaire.

Réutiliser autant que possible :

- les composants existants ;
- les modèles de données ;
- les services ;
- les règles ;
- les calculs ;
- les images des technologies ;
- les données des technologies ;
- les mécanismes de sauvegarde ;
- le système de tour existant.

La priorité est une **refonte UX/UI de la partie**, pas une réarchitecture complète.

---

## Ne pas faire d'over-engineering

Ne pas ajouter :

- moteur de jeu externe ;
- moteur 3D ;
- Three.js ;
- architecture complexe inutile ;
- Redux-like supplémentaire si l'application n'en utilise pas déjà ;
- système générique d'animations disproportionné ;
- framework UI supplémentaire sans raison forte.

CSS, animations web classiques et composants existants doivent suffire.

---

# 3. Passer en véritable « mode jeu »

Quand une partie est ouverte, créer un mode visuel spécifique.

L'écran doit utiliser au maximum :

```text
100vw × 100vh
````

La partie doit donner l'impression d'occuper tout l'écran.

Éviter autant que possible :

* le scroll global de la page ;
* les breadcrumbs ;
* les gros titres de page ;
* les panneaux d'administration ;
* les menus applicatifs permanents.

La navigation générale de l'application peut rester accessible via un bouton discret, par exemple :

```text
☰
```

mais elle ne doit plus dominer visuellement l'écran.

Les interfaces :

* règles ;
* éditeur ;
* accueil ;
* paramètres ;

restent inchangées pour cette étape.

---

# 4. Nouvelle organisation générale

Réorganiser l'écran autour de trois espaces fonctionnels.

## Zone haute

Afficher de manière compacte :

* décennie / année actuelle ;
* numéro du tour ;
* score de prospérité ;
* argent ;
* éventuellement le joueur actif.

Exemple :

```text
1970                         100 €       0 PP
Tour 1 / 36
```

Cette zone doit ressembler à une information de jeu et non à une barre d'administration.

---

# 5. Le plateau de recherche doit devenir central

Le système actuel présentant les technologies comme un catalogue ou une grille indépendante doit évoluer.

Créer une vraie représentation spatiale de la recherche.

Le joueur doit comprendre visuellement la relation entre :

```text
technologie
    ↕
niveau de recherche
    ↕
coût
```

Représenter les deux branches :

```text
ÉNERGIE             RECHERCHE              ÉCOLOGIE
```

avec les niveaux :

```text
6
5
4
3
2
1
```

Les technologies doivent être visuellement rattachées au niveau correspondant.

Par exemple :

```text
ÉNERGIE            RECHERCHE             ÉCOLOGIE

[tile] [tile]          6             [tile] [tile]

[tile]                 5             [tile]

[tile] [tile]          4             [tile]

                        3

                        2

                        1
```

Ne pas nécessairement reproduire graphiquement le plateau physique original.

L'objectif est de conserver sa logique spatiale.

---

# 6. Remplacer les niveaux textuels par de vrais marqueurs

Les pistes de recherche ne doivent plus principalement ressembler à :

```text
Recherche énergie

1 2 3 4 5 6
```

Créer une vraie piste.

Le niveau du joueur doit être représenté par un marqueur visuel :

* cube ;
* pion ;
* disque ;
* élément équivalent cohérent avec la direction artistique.

Quand le niveau change :

* le pion se déplace visuellement ;
* utiliser une petite animation ;
* ne pas simplement changer un chiffre.

Prévoir dès maintenant la possibilité d'afficher plusieurs marqueurs si le multijoueur est utilisé.

---

# 7. Technologies : supprimer l'effet « catalogue »

Ne plus utiliser comme représentation principale :

* recherche texte ;
* dropdown de type ;
* grille façon boutique ;
* scrollbar dans un catalogue.

Les technologies doivent être visibles comme des **éléments du plateau**.

Les filtres peuvent éventuellement rester disponibles dans une fonction secondaire, mais ils ne doivent pas définir l'expérience principale.

---

# 8. Interaction avec une technologie

Au survol d'une technologie :

* légère élévation ;
* mise en avant ;
* information minimale ;
* coût pour le joueur si pertinent.

Au clic, afficher les informations sans systématiquement utiliser une grosse modale bloquante.

Privilégier :

* panneau contextuel ;
* popover ;
* carte agrandie ;
* zone de détail intégrée au plateau.

La grande modale peut rester utilisée lorsqu'une décision complexe le justifie.

---

# 9. Afficher un coût contextualisé

Ne pas simplement afficher :

```text
100 €
```

Expliquer pourquoi le joueur paie ce prix.

Exemples :

```text
100 €
Même niveau que votre recherche
```

ou :

```text
200 €
1 niveau au-dessus de votre recherche
```

ou :

```text
50 €
Technologie inférieure à votre niveau
```

Cette explication doit être discrète mais accessible.

---

# 10. Aperçu des conséquences d'un achat

Lorsqu'une technologie est sélectionnée, afficher les conséquences pour le joueur.

Exemple :

```text
TRAIN À GRANDE VITESSE

Transport
Recherche écologie : niveau 3

Votre recherche : 3
Prix : 100 €

             AVANT     APRÈS

Énergie        +1        0
Écologie       -1       -1
Capital         1        3
Recherche       2        2
Prospérité      0        0
```

Ne montrer que les statistiques pertinentes.

L'interface doit aider le joueur à prendre sa décision sans modifier les règles.

---

# 11. Le territoire doit devenir manipulable

Le territoire est l'un des éléments principaux de l'écran.

Augmenter son importance visuelle.

Lorsqu'une technologie pouvant être placée est achetée :

1. la tuile doit visuellement quitter sa zone d'origine ;
2. le territoire devient la zone active ;
3. les emplacements compatibles sont mis en évidence ;
4. les emplacements impossibles sont atténués ;
5. le joueur sélectionne l'emplacement ;
6. la technologie est placée avec une animation légère.

Un drag & drop est souhaitable si cela reste fiable.

Sinon utiliser :

```text
clic technologie
→ clic emplacement
```

avec une excellente représentation visuelle.

La fiabilité est plus importante qu'un drag & drop fragile.

---

# 12. Remplacement de technologie

Prosperity permet de placer une nouvelle technologie sur une technologie existante.

Cette mécanique doit être immédiatement compréhensible.

Au survol d'un emplacement occupé, afficher par exemple :

```text
Centrale au charbon
        ↓
Centrale au fioul
```

et les différences :

```text
Énergie     +2 → +4
Écologie    -1 → -2
```

Après validation :

* nouvelle technologie placée au-dessus ;
* ancienne technologie visuellement remplacée ;
* petite animation ;
* les valeurs du plateau se mettent à jour.

Ne pas ajouter de popup de confirmation inutile si l'action peut être annulée avant validation.

---

# 13. Emplacements verrouillés

Les emplacements nécessitant préalablement un transport doivent être visuellement explicites.

Éviter un simple emplacement grisé.

Utiliser par exemple :

* route interrompue ;
* cadenas intégré au plateau ;
* connexion manquante ;
* pictogramme transport.

Lorsqu'un transport compatible est construit :

* montrer visuellement que les emplacements deviennent accessibles.

Animation très légère suffisante.

---

# 14. Repenser complètement la pollution

La pollution est une mécanique majeure du jeu.

Elle est actuellement trop proche d'un indicateur statistique.

Créer une vraie **piste physique de pollution**.

Représenter les jetons de pollution comme des disques réellement posés sur le plateau.

Exemple conceptuel :

```text
POLLUTION

● ● ● ● ● ● ● ●
──────────────────
      PP     PP    ☣
```

Quand un jeton est ajouté :

```text
nouveau disque
↓
placement sur la piste
```

Quand un jeton est retiré :

```text
disque
↓
petite animation
↓
disparition
↓
élément éventuellement caché révélé
```

Les symboles de prospérité masqués par la pollution doivent pouvoir être découverts visuellement.

La dernière zone dangereuse doit être beaucoup plus lisible.

Si le joueur atteint une situation empêchant de marquer des points de prospérité, cela doit être immédiatement compréhensible.

Ne pas se contenter d'une couleur rouge.

Utiliser une représentation cohérente avec le plateau.

---

# 15. Donner une existence physique aux ressources

Les informations importantes doivent avoir une représentation visuelle plus ludique.

Par exemple :

## Argent

Au lieu de seulement modifier :

```text
100 €
```

faire apparaître brièvement :

```text
100 € → 200 €
+100 €
```

## Recherche

Déplacer le pion.

## Score

Déplacer visuellement un marqueur ou animer légèrement la valeur.

## Pollution

Déplacer les disques.

L'objectif n'est PAS de créer de grosses animations.

Durée recommandée :

```text
150 à 500 ms
```

selon l'action.

---

# 16. Repenser complètement le déroulement du tour

Le tour doit être vécu comme une succession d'étapes.

Éviter un simple bandeau :

```text
Votre tour
[Révéler la première tuile]
```

Créer un système beaucoup plus proche d'une séquence de jeu.

---

## Étape 1 — Révélation

Afficher par exemple :

```text
1970
Tour 1 / 36

[ DOS DE TUILE ]

Révéler la technologie
```

Au clic :

* animation courte de révélation ;
* flip ou apparition ;
* technologie mise en avant.

---

## Étape 2 — Décompte

Afficher clairement le symbole déclenché.

Exemple :

```text
DÉCOMPTE ÉNERGIE
⚡
```

Mettre momentanément en évidence :

* les valeurs concernées ;
* les conséquences.

Exemple :

```text
Énergie : +2

+100 €
```

Le joueur doit comprendre ce qui vient de se produire.

Éviter de simplement modifier silencieusement les valeurs.

---

## Étape 3 — Actions

Une fois le décompte terminé :

```text
VOTRE TOUR

● ●

2 actions restantes
```

Afficher les quatre types d'actions principales de manière accessible :

```text
Revenu
Dépolluer
Recherche
Acheter une technologie
```

Après une action :

```text
● ○

1 action restante
```

Après la seconde :

```text
○ ○

Terminer le tour
```

Le joueur peut effectuer deux fois la même action si les règles le permettent.

Ne pas bloquer artificiellement cette possibilité.

---

# 17. Les actions doivent être contextuelles

Éviter quatre énormes boutons constamment présents.

L'écran doit réagir au mode choisi.

Exemple :

## Recherche

Si le joueur choisit :

```text
Recherche
```

mettre en évidence les deux pistes.

Le joueur clique ensuite sur :

```text
Énergie
```

ou :

```text
Écologie
```

Le pion avance.

---

## Dépolluer

Si le joueur choisit :

```text
Dépolluer
```

mettre la piste Pollution en évidence.

Puis retirer visuellement un disque.

---

## Technologie

Si le joueur choisit :

```text
Acheter
```

mettre les technologies disponibles en évidence.

Les autres éléments passent légèrement au second plan.

---

# 18. Utiliser une hiérarchie visuelle dynamique

Actuellement trop d'éléments ont une importance visuelle similaire.

Changer cela.

L'élément correspondant à l'action courante doit devenir dominant.

Exemples :

## Pendant la révélation

Dominant :

```text
nouvelle technologie
```

## Pendant un décompte écologique

Dominants :

```text
écologie
pollution
```

## Pendant une recherche

Dominants :

```text
pistes de recherche
```

## Pendant un achat

Dominants :

```text
technologies
recherche
territoire
```

Les autres éléments ne doivent pas disparaître.

Réduire simplement légèrement leur contraste ou leur importance.

---

# 19. Animations

Ajouter uniquement des animations fonctionnelles.

Animations souhaitées :

* flip d'une technologie révélée ;
* déplacement d'une technologie achetée ;
* placement d'une technologie ;
* déplacement d'un pion de recherche ;
* ajout / retrait d'un disque de pollution ;
* variation d'argent ;
* variation de score ;
* consommation d'une action.

Éviter :

* particules permanentes ;
* glow excessif ;
* bounce partout ;
* animations longues ;
* transitions de page spectaculaires ;
* effets mobiles gratuits.

Le jeu doit rester calme et stratégique.

---

# 20. Son

Prévoir une architecture très légère permettant éventuellement :

* bruit de tuile ;
* bruit de pion ;
* bruit de jeton ;
* bruit de monnaie.

Mais :

* le son ne doit pas être obligatoire ;
* prévoir un bouton mute ;
* ne pas bloquer cette étape sur la création des sons.

Si aucun asset audio propre n'est disponible, laisser simplement le système prêt sans ajouter de mauvais sons temporaires.

---

# 21. Direction artistique

Conserver globalement l'identité actuelle.

Elle fonctionne bien :

* tons crème ;
* vert foncé ;
* illustrations isométriques ;
* touches dorées ;
* typographie élégante.

Ne pas effectuer de refonte graphique totale.

Il faut surtout modifier :

* composition ;
* hiérarchie ;
* spatialisation ;
* interactions ;
* animations ;
* sensation physique.

Éviter absolument un résultat :

* mobile-game générique ;
* SaaS dashboard ;
* glassmorphism ;
* cyberpunk ;
* néon ;
* gamification excessive.

Prosperity doit rester un jeu de plateau de gestion élégant et sobre.

---

# 22. Responsive

La priorité est :

```text
desktop
```

L'application doit rester utilisable sur des écrans courants tels que :

```text
1920×1080
2560×1440
1440×900
1366×768
```

Éviter le scroll global dans la mesure du possible.

Pour les petits écrans, réduire progressivement certains éléments sans casser le plateau.

Le mobile n'est PAS une priorité pour cette étape.

Ne pas dégrader l'expérience desktop pour obtenir artificiellement une parfaite compatibilité mobile.

---

# 23. UX

Toutes les actions doivent respecter les principes suivants.

## Immédiatement compréhensible

Un joueur doit savoir :

* ce qu'il peut faire ;
* ce qui est sélectionné ;
* combien d'actions lui restent ;
* quelle étape du tour est en cours.

## Pas de popup inutile

Éviter :

```text
Êtes-vous sûr ?
```

pour chaque action.

## Undo

Si l'architecture actuelle permet facilement un retour arrière avant validation définitive du tour, le conserver ou l'améliorer.

Ne pas construire un système complexe d'historique si celui-ci n'existe pas déjà.

## Tooltips

Les utiliser pour compléter l'interface.

Ne pas cacher des informations indispensables uniquement dans des tooltips.

---

# 24. Accessibilité visuelle

Ne jamais transmettre une information uniquement par la couleur.

Associer autant que possible :

```text
couleur + symbole + texte éventuel
```

Exemple :

```text
⚡ Énergie
🌿 Écologie
```

Conserver des contrastes suffisants.

---

# 25. Ce qui ne doit PAS être traité dans cette étape

Ne pas travailler sur :

* éditeur de technologies ;
* interface des règles ;
* nouvelles règles ;
* équilibrage ;
* IA adversaire ;
* campagne ;
* succès ;
* classement ;
* comptes utilisateurs ;
* matchmaking ;
* chat ;
* nouvelles technologies ;
* DLC ;
* tutoriel complet ;
* refonte du backend ;
* multijoueur réseau si celui-ci n'existe pas déjà.

Ne pas ajouter de fonctionnalités qui pourraient appartenir à une future version.

---

# 26. Méthode d'implémentation

Commence par analyser l'application existante.

Identifier :

1. le composant principal de partie ;
2. les composants du territoire ;
3. les technologies ;
4. la recherche ;
5. la pollution ;
6. le système de tour ;
7. les actions ;
8. les états déjà disponibles.

Réutiliser les données existantes.

Ne pas dupliquer la logique métier dans les composants UI.

---

# 27. Priorité d'implémentation

Implémenter dans cet ordre.

## P0 — indispensable

1. Mode jeu plein écran.
2. Suppression de l'aspect dashboard.
3. Nouveau layout général.
4. Plateau recherche / technologies spatial.
5. Vraies pistes de recherche avec marqueurs.
6. Nouvelle représentation de la pollution.
7. Séquence visuelle :

   * révélation ;
   * décompte ;
   * deux actions.
8. Compteur visuel des deux actions.
9. Mise en avant contextuelle de l'action active.
10. Achat et placement d'une technologie sur le territoire.

## P1 — important

11. Aperçu avant/après d'une technologie.
12. Explication du coût.
13. Animations des marqueurs.
14. Animations de pollution.
15. Animations d'argent et score.
16. Représentation améliorée du remplacement d'une technologie.
17. Emplacements verrouillés plus explicites.

## P2 — uniquement si P0 et P1 sont propres

18. Drag & drop des technologies.
19. Micro-interactions supplémentaires.
20. Support léger des sons.

Ne pas commencer P2 tant que P0 n'est pas réellement abouti.

---

# 28. Critères de validation

La refonte sera considérée réussie si :

### Critère 1

En regardant l'écran sans contexte, il ressemble davantage à :

> un jeu de plateau numérique

qu'à :

> une application de gestion.

### Critère 2

Le joueur comprend immédiatement :

```text
année
tour
argent
score
pollution
recherche énergie
recherche écologie
nombre d'actions restantes
étape actuelle
```

### Critère 3

Une technologie peut être achetée sans devoir naviguer dans un catalogue administratif.

### Critère 4

La relation entre :

```text
recherche
niveau technologie
prix
```

est visuellement compréhensible.

### Critère 5

La pollution ressemble à une mécanique du jeu et non à un indicateur secondaire.

### Critère 6

Une augmentation de recherche produit un déplacement visible d'un marqueur.

### Critère 7

Le joueur voit clairement :

```text
● ●
```

puis :

```text
● ○
```

puis :

```text
○ ○
```

pendant ses actions.

### Critère 8

Lorsqu'une technologie est achetée, le joueur comprend immédiatement :

* où elle peut être placée ;
* ce qu'elle remplace ;
* son impact sur son pays.

### Critère 9

Le fonctionnement métier actuel de Prosperity n'a pas été cassé.

---

# 29. Qualité du code

Le code final doit rester :

* simple ;
* maintenable ;
* lisible ;
* découpé raisonnablement ;
* cohérent avec l'architecture actuelle.

Ne pas créer un composant gigantesque contenant toute la partie.

Mais ne pas non plus transformer chaque élément graphique en abstraction générique prématurée.

Créer des composants correspondant à de vrais concepts du jeu.

Exemples possibles :

```text
GameBoard
TurnFlow
ResearchBoard
ResearchTrack
TechnologyTile
TechnologyDetails
PlayerTerritory
PollutionTrack
ActionTokens
GameStatus
```

Les noms exacts doivent être adaptés à l'architecture existante.

---

# 30. Résultat attendu

Tu dois directement modifier et implémenter l'application.

Ne produis pas seulement :

* une analyse ;
* un plan ;
* des maquettes textuelles ;
* des recommandations.

Tu peux commencer par inspecter le code et établir mentalement la stratégie de modification, mais ensuite implémente réellement la refonte.

Après l'implémentation :

1. vérifier que l'application compile ;
2. corriger les erreurs ;
3. vérifier les interactions principales ;
4. vérifier qu'une partie peut toujours progresser ;
5. vérifier qu'aucune règle existante n'a été involontairement modifiée.

La priorité absolue est :

> Faire de l'écran de partie une table de jeu interactive, lisible et agréable à manipuler, tout en conservant strictement le moteur et les règles existantes de Prosperity.
